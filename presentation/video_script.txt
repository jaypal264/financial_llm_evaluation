[Slide 2 — Problem Statement and Motivation]
"Large Language Models have shown remarkable capabilities across many domains, but how 
well do they actually perform on specialized financial tasks? This matters enormously 
because financial analysis requires three things that general-purpose LLMs struggle with:
precise numerical reasoning over earnings tables, accurate retrieval from dense financial 
documents like SEC 10-K filings, and faithfulness — meaning the model must not hallucinate 
facts that could lead to incorrect investment decisions or compliance failures.

Our project addresses a simple but important question: among the best open-weight LLMs 
available today, which one is most reliable for financial question answering, and does 
Retrieval-Augmented Generation improve their accuracy?"

[Slide 3 — Research Questions]
"We designed four research questions to guide our study.
First: Which open-weight LLM achieves the highest accuracy on financial QA benchmarks?
Second: Does RAG — Retrieval-Augmented Generation — improve LLM performance compared to 
direct answering?
Third: Which model performs best specifically on numerical reasoning versus conceptual questions?
And fourth: What is the latency and cost trade-off across models?
These questions drive our experimental design."

[Slide 4 — Dataset: FinanceBench]
"We used three established financial benchmarks.

The first is FinanceBench, created by PatronusAI. This dataset contains questions drawn 
from real SEC filings — 10-K and 10-Q reports from public companies. The questions require 
understanding financial documents, extracting specific figures, and performing multi-step 
calculations. The public sample contains 150 questions. We want to be clear that the full 
benchmark has over 10,000 questions, but only 150 are publicly available, so our evaluation 
is on that public portion."

[Slide 5 — Dataset: FinTextQA]
"The second dataset is FinTextQA, presented at ACL 2024 by Chen and colleagues. It focuses 
on long-form financial question answering over policy and regulatory documents. The public 
release contains approximately 240 question-answer pairs from financial regulations. We note 
that the textbook portion described in the paper is not publicly available, so we document 
this limitation explicitly."

[Slide 6 — Dataset: FinQA]
"The third dataset is FinQA, from the 2021 EMNLP paper by Zhiyu Chen and colleagues. 
FinQA is specifically designed for numerical reasoning over financial tables and text. 
Each question comes with an earnings report table, pre- and post-table text, and a 
reference program showing the step-by-step calculation. We use the official test split 
for evaluation."

[Slide 7 — Dataset Statistics]
"Let me summarize our dataset statistics. [Reference the actual numbers from your notebook output]
FinanceBench: 150 publicly available questions, mixed question types.
FinTextQA: approximately 240 questions focused on regulatory content.
FinQA test split: approximately 1,147 questions requiring numerical reasoning.

The key difference is that FinQA has by far the highest proportion of numerical answers, 
making it the most challenging for exact numeric accuracy. FinanceBench has the richest 
metadata including company names and document references. FinTextQA provides the longest 
context passages."

[Slide 8 — Six LLMs]
"For our evaluation, we selected six diverse open-weight Large Language Models.

First, Qwen 2.5 7B Instruct — from Alibaba's Qwen family, known for strong multilingual 
and mathematical capabilities.

Second, Llama 3.1 8B Instruct — Meta's latest open-weight model with significant 
improvements in instruction following.

Third, Mistral 7B Instruct version 0.3 — from Mistral AI, known for efficiency and 
strong benchmark performance relative to its size.

Fourth, Gemma 2 9B IT — Google's instruction-tuned Gemma model at 9 billion parameters.

Fifth, Phi 3.5 mini — Microsoft's compact model with strong performance despite having 
only 3.8 billion parameters.

And sixth, DeepSeek R1 Distill Qwen 7B — a reasoning-focused model from DeepSeek, 
distilled with chain-of-thought training, which we expect to excel at multi-step 
numerical problems.

We selected these models to represent diversity across model families, sizes, and training 
approaches, while remaining within open-weight access constraints."

[Slide 9 — Experimental Methodology]
"Our experimental design ensures a fair comparison. All six models receive identical prompts 
and identical generation parameters. Temperature is set to zero for greedy deterministic 
decoding, ensuring reproducibility. Maximum new tokens is 512 for all models.

We use the Hugging Face Inference Providers API as our primary inference backend, 
providing a consistent OpenAI-compatible endpoint for all models. This is crucial — 
using the same API prevents infrastructure differences from confounding our results.

We implemented full checkpoint and resume functionality, so if the evaluation is interrupted, 
it resumes without re-calling any already-completed API endpoint."

[Slide 10 — Experiment A: Direct LLM]
"Experiment A is our baseline. We provide each model with the question and the benchmark's 
provided context — the relevant section from the financial document or table — and ask for 
an answer. This measures how well the model can use already-retrieved evidence.

The prompt follows a consistent structure: a system message defining the model's role as 
a financial analyst, followed by the financial context and the question."

[Slide 11 — Experiment B: RAG Architecture]
"Experiment B adds a retrieval layer. Our RAG pipeline works in five steps.

One: We build a retrieval corpus from all available contexts across all three datasets. 
Critically, reference answers are never included in the corpus — only the document text.

Two: We chunk documents into 400-word overlapping segments with 50-word overlap.

Three: We generate dense embeddings using the sentence-transformers all-MiniLM-L6-v2 model.

Four: We index these embeddings in FAISS — a highly efficient approximate nearest neighbor 
library — for fast retrieval.

Five: At query time, we retrieve the top 5 chunks most similar to the question, provide 
them as context to the LLM, and generate the answer.

We also implement BM25 as a sparse retrieval baseline to compare dense versus sparse retrieval."

[Slide 12 — Evaluation Metrics]
"We evaluate model performance across five metric categories.

For answer correctness: Exact Match, Token-level F1 as used in SQuAD, and ROUGE-L which 
measures longest common subsequence overlap.

For numerical accuracy: We extract the primary numeric value from both the predicted and 
reference answer, normalize currency symbols and percentage formatting, and apply a 
0.5% relative error tolerance.

For answer quality: We compute BERTScore using contextual embeddings, and semantic 
similarity using sentence-transformers.

For faithfulness: We compute a lexical proxy measuring what fraction of the model's 
content tokens actually appear in the provided context. We also detect abstention — 
cases where the model correctly says it doesn't know rather than hallucinating.

And for efficiency: we record latency, token usage, and estimated API cost per model."

[Slide 16 — Limitations]
"We want to be transparent about our limitations.

First, our evaluation uses only the publicly available portions of each benchmark. 
FinanceBench's full 10,231 questions are not public. FinTextQA's textbook portion is 
not released. Our results therefore cannot claim to represent performance on the full 
benchmarks.

Second, our faithfulness metric is a lexical proxy, not a full NLI-based faithfulness 
evaluation. A model could score high on lexical faithfulness while still making incorrect 
numerical inferences.

Third, Exact Match is a strict metric — a correct answer expressed with different wording 
scores zero. This means our EM scores underestimate true answer quality, particularly for 
FinTextQA's long-form answers.

Fourth, we used greedy decoding for reproducibility, but temperature sampling might 
improve some models' performance."
